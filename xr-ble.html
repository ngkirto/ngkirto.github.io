01 / THE DEVICE LAYER

One interface for every controller

XRCC behaviours don't know whether a value came over BLE or a USB cable. They talk to IMCUController, and each transport implements it. Adding a new kind of controller means adding one class, not changing the behaviours.

For several BLE devices at once, the DLL hands back data from every device through one poll call. A single receive thread is the only thing that polls it: it reads each packet, looks up the device it came from and passes it to that device's controller, so no controller can steal another's data.

The Micro:bit's UART service names TX and RX the opposite way round to Nordic's, so the Micro:bit controller swaps the two characteristics. Looking back, that's a configuration difference rather than a behaviour, and BLE 2 handles it as data instead of a subclass.

02 / WHERE V1 HIT ITS LIMITS

The library underneath

v1 worked, and it still runs both demos. But BleWinrtDll, the open-source library underneath, was built for one device and short tests, and the more devices I added, the more of its limits showed:

  • Results carry no device. The library returns service and characteristic results through one shared queue. Its connect call blocks, so devices connect one at a time and the results never mix, but connecting N devices takes N times as long and can never run in parallel.
  • Locks shared with its own handlers. The library's connection-status check takes the same lock as its Bluetooth event handlers, so polling it often can deadlock against them while the app is stopping.
  • Errors aren't contained. Some exceptions inside the library aren't caught at its boundary, so one failed call can't simply be reported back to the caller.
  • Windows only. The library is built on WinRT, so there was no path for phones.
03 / BLE 2

A rewrite, rule by rule

BLE 2 replaces the DLL and the C# wrapper. It follows the design of bleak, the open-source Python BLE library: every request returns an id, and its result comes back later as one event tagged with that id and the device it belongs to.

Each device gets its own worker thread that owns its Bluetooth objects. A single C# pump drains the event queue and hands results back to Unity's main thread, so nothing in Unity ever waits on the radio.

BLE is now its own Unity package rather than part of the microcontroller code, because phones connect to XRCC over BLE too. A single profile file generates the matching constants for C#, Kotlin and Swift.

BLEWINRTDLL LIMITBLE 2 RULE
Calls marked non-blocking can still block the caller.One worker thread per device. Every call posts its work and returns at once.
The status check shares a lock with the library's event handlers and can deadlock against them.No lock is held across a Bluetooth call. Event handlers only copy data into the queue.
Some exceptions escape the library's boundary instead of becoming errors.Every exported call and every handler is wrapped; a failure becomes a status code.
One service and characteristic queue for all devices.Every result is an event tagged with its device and request id.
Its shutdown doesn't wait for work still in flight.Shutdown cancels requests, releases each device on its own thread and joins it, with a deadline.
04 / TESTING

A stress runner with written pass rules

BLE 2 comes with a .NET stress runner built from the same C# sources Unity uses. Each scenario has a pass rule written down before it runs, so "stable" means a number, not a feeling:

SCENARIOPASS RULE
Self-test, adapter, scan, advertise, GATT serverExact round trips for UUIDs, advertising data and frames; scanning and advertising start and stop cleanly.
Lifecycle × 40Start everything, hammer it from another thread, shut down: every shutdown under 3.5 s, every request completes, no handle or thread growth.
Against a real peer: reconnect, 1-hour soak, echo, concurrent≥ 95 % reconnects, ≥ 99 % echoes, echo p95 under 100 ms, nothing stuck.

05 / BUILT WITH AI

What I did, and what Claude did

v1 is my own code, written over two demos. For BLE 2, Claude wrote most of the new code, following bleak's design across Windows, Android and iOS.

My part was knowing what had to change: the library limits above come from running the demos and tracing each problem back to its cause. Those causes became the rules the rewrite had to follow, and the stress runner is how I check it really does.
